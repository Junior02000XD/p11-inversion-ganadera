Sección 1

La API en un minuto

En breve

Es una Web API REST en ASP.NET Core (.NET 10): recibe y devuelve JSON por HTTPS, guarda en SQL Server con EF Core y sabe quién llama gracias a un token JWT. La usan la web (React) y, más adelante, la app Android.

Qué es

El programa del servidor que aplica las reglas del negocio: quién puede postular un proyecto, cuánto cupo queda, cuándo vence una reserva.

Con qué está hecha

ASP.NET Core con controladores, EF Core + SQL Server, ASP.NET Core Identity (usuarios y contraseñas), JWT Bearer, OpenAPI con Swagger UI y Scalar.

Dónde vive

apps/api/ (la API) y tests/api/ (sus pruebas). P11.sln abre las dos en Visual Studio o Rider.

Dónde se prueba

Swagger UI en https://localhost:7080/swagger, Scalar en /scalar y los correos de prueba en http://localhost:8025.

Qué significa que sea REST

  • Recursos con URL propia: /api/proyectos es la colección; /api/proyectos/{id}, uno; /api/proyectos/{id}/historial, un recurso relacionado.
  • El verbo HTTP dice la acción: GET consulta, POST crea o ejecuta una acción, PUT reemplaza, DELETE elimina.
  • Sin estado en el servidor: no hay sesión guardada. Cada petición trae su token y la API la resuelve sola. Por eso escala y por eso la app Android podrá usar la misma API.
  • El código de respuesta tiene significado: 201 creado, 404 no existe, 409 choca con una regla (sección 8).

Las acciones que no son «crear, leer, cambiar o borrar» se modelan como POST a una sub-ruta con verbo: POST /api/proyectos/{id}/enviar-revision o POST /api/inversiones/{id}/contrato/firmar. Es la forma habitual de expresar una transición de estado en REST.

Sección 2

Recorrido de una petición

En breve

Cada petición pasa por una fila de middlewares en el orden en que están en Program.cs. Cualquiera puede cortarla y responder antes: la autenticación con 401, la autorización con 403, la validación del DTO con 400. Si llega al controlador, este usa servicios y EF Core, y devuelve un DTO que se convierte en JSON.

  1. El cliente arma la petición. La web llama a /api/... y agrega la cabecera Authorization: Bearer <token> si hay sesión. apps/web/src/api.js → pedir()
  2. HTTPS obligatorio. Si llega por http, se redirige a https: el token y las contraseñas nunca viajan en claro. Program.cs → app.UseHttpsRedirection()
  3. Autenticación: ¿quién eres? El middleware JwtBearer lee el token, revisa firma, emisor, audiencia y vencimiento, y arma User con sus claims. Si no hay token, sigue como anónimo; si el token es inválido y la ruta lo exige, responde 401. Program.cs → AddJwtBearer + app.UseAuthentication()
  4. Autorización: ¿puedes hacer esto? Mira el [Authorize(Roles = …)] del controlador. Sin identidad, 401; con identidad pero sin el rol, 403. Program.cs → app.UseAuthorization()
  5. El controlador recibe el DTO ya validado. Por [ApiController], si el JSON no cumple los [Required], [Range], etc., ASP.NET responde 400 solo, sin entrar a la acción. Controllers/*.cs
  6. Reglas y base de datos. La acción pide ayuda a servicios y a las clases del dominio (por ejemplo el State del proyecto) y guarda con db.SaveChangesAsync(). Una regla rota se traduce en 404 o 409. Services/, Models/, Data/AppDbContext.cs

El orden importa: UseAuthentication() va antes de UseAuthorization(), y las dos antes de MapControllers(). Si se invierten, la autorización corre sin saber quién es el usuario y todas las rutas protegidas dan 401.

app.UseAuthentication();
app.UseAuthorization();

  • Después de Build() se arma el pipeline: el camino de la sección 2.

  • Swagger y Scalar se publican solo en Development: en producción no se expone el mapa de la API.

Sección 4

Inicio de sesión y JWT

En breve

Identity comprueba correo y contraseña contra la base (con hash y bloqueo al 5.º intento). Si está bien, TokenJwtService firma un JWT con HS256 que dice quién es (sub), su correo y su rol, y vence en 120 minutos. El cliente lo manda en cada petición como Authorization: Bearer … y el middleware lo valida sin consultar la base.

Qué lleva el token

Un JWT son tres partes en base64url separadas por puntos: cabecera (algoritmo), contenido (los claims) y firma. El contenido se puede leer sin la clave: no es secreto, solo es imposible de cambiar sin invalidar la firma. Por eso no lleva la contraseña ni nada privado.

Cómo se emite

  

    
apps/api/Services/Auth/TokenJwtService.cs


public TokenEmitido Emitir(Usuario u, IEnumerable<string> roles)
{
    var expira = reloj.GetUtcNow().AddMinutes(_o.MinutosVigencia);   // 120 min (appsettings)
    var claims = new List<Claim>
    {
        new(JwtRegisteredClaimNames.Sub, u.Id.ToString()),
        new(JwtRegisteredClaimNames.Email, u.Email ?? ""),
        new(JwtRegisteredClaimNames.Jti, Guid.NewGuid().ToString()),
    };
    claims.AddRange(roles.Select(r => new Claim(ClaimRol, r)));    // "role"

    var credenciales = new SigningCredentials(ClaveDeFirma(_o), SecurityAlgorithms.HmacSha256);
    var jwt = new JwtSecurityToken(_o.Emisor, _o.Audiencia, claims,
        notBefore: reloj.GetUtcNow().UtcDateTime, expires: expira.UtcDateTime, signingCredentials: credenciales);
    return new TokenEmitido(new JwtSecurityTokenHandler().WriteToken(jwt), expira);
}

// La clave se guarda en base64 y se usan sus bytes reales (32 o más)
public static SymmetricSecurityKey ClaveDeFirma(JwtOptions o) => new(Convert.FromBase64String(o.ClaveFirma));

  


  
Cómo se valida

  

    
apps/api/Program.cs


bearer.MapInboundClaims = false;          // los claims quedan con su nombre corto: "sub", "role"
bearer.TokenValidationParameters = new TokenValidationParameters
{
    ValidateIssuer = true,            ValidIssuer = jwt.Emisor,
    ValidateAudience = true,          ValidAudience = jwt.Audiencia,
    ValidateIssuerSigningKey = true,  IssuerSigningKey = TokenJwtService.ClaveDeFirma(jwt),
    RequireSignedTokens = true,
    ValidAlgorithms = [SecurityAlgorithms.HmacSha256],   // ni "none" ni otro algoritmo
    RequireExpirationTime = true,     ValidateLifetime = true,
    ClockSkew = TimeSpan.Zero,        // vence en el segundo exacto
    RoleClaimType = TokenJwtService.ClaimRol,     // de dónde lee [Authorize(Roles)]
    NameClaimType = TokenJwtService.ClaimCorreo,
};

  

  
    
    
  • HS256 es simétrico: la misma clave firma y verifica. Sirve porque la API es la única que emite y la única que valida. Si otro servicio tuviera que validar sin poder firmar, convendría RS256 (clave pública y privada).
    • 
    
  • La clave nunca está en el repositorio. En desarrollo la genera ClavesDesarrollo en App_Data/claves-desarrollo.json (ignorado por git); fuera de desarrollo debe venir de user-secrets o de una variable de entorno, o la API no arranca (ValidateOnStart).
    • 
    
  • Validar no consulta la base: por eso es rápido y por eso un token sigue valiendo hasta que vence aunque cambie el rol (ver 19).
    • 
    
  • 120 minutos y no 15: no hay refresh token, así que un token corto sacaría al usuario a mitad de una inversión (reserva de 30 min + contrato + pago). Se configura en Jwt:MinutosVigencia.

Sección 5

  
Comparación con la práctica del Carrito

  
En breve
La validación del token es la misma que en la guía de clase (firma, emisor, audiencia, vencimiento, solo HS256, sin margen de reloj). Lo que cambia es todo lo de alrededor: usuarios reales con Identity en vez de un usuario fijo en user-secrets, roles dentro del token y datos filtrados por usuario con sub.

Sección 6

  
Roles y dueño del dato

  
En breve
Hay dos controles distintos. El rol decide a qué controlador entras ([Authorize(Roles)] → 403 si no corresponde). El dueño decide qué filas ves dentro: cada consulta se filtra por el sub del token, y lo que no es tuyo responde 404 como si no existiera.


  

    
Inversionista
Catálogo, simulador, inversiones, portafolio, verificación de identidad. Se registra solo.

    
Productor
Fichas de proyecto, documentos del predio, verificación de identidad. Se registra solo.

    
Analista
Evaluar y publicar proyectos, revisar identidades y documentos. Lo crea la semilla o el administrador.

    
Administrador
Usuarios, roles y bitácora; además entra a las rutas de analista, productor e inversionista (salvo enviar su propia verificación de identidad).

  


  

    
apps/api/Controllers/ProyectosController.cs


[ApiController]
[Route("api/proyectos")]
[Authorize(Roles = $"{Roles.Productor},{Roles.Administrador}")]   // coma = cualquiera de los dos
public class ProyectosController(AppDbContext db, …) : ControllerBase
{
    /// El productor ve solo los suyos; el administrador, todos.
    private IQueryable<ProyectoGanadero> Visibles()
    {
        if (EsAdministrador) return db.Proyectos;
        var productorId = User.IdUsuario();                           // el "sub" del token
        return db.Proyectos.Where(p => p.ProductorId == productorId);
    }
}

  

  
    
    
  • Los nombres de los roles son constantes en Models/Roles.cs: un error de tipeo no compila, en vez de dejar una ruta sin acceso.
    • 
    
  • El id del dueño sale del token, nunca del cuerpo de la petición. Si viniera del JSON, cualquiera podría crear proyectos a nombre de otro.
    • 
    
  • 404 y no 403 para lo ajeno: así no se confirma que ese id existe. El 403 queda para «tu rol no puede usar esta ruta».
    • 
    
  • Un rol nuevo asignado por el administrador rige desde el próximo inicio de sesión, porque el rol viaja dentro del token.
    • 
  

  

    
  







  
Sección 7

  
Todos los endpoints

  
En breve
Once controladores, uno por tema. El recurso principal es /api/proyectos (CRUD completo) y su recurso relacionado es /api/proyectos/{id}/historial. Las rutas con {id:guid} solo aceptan un Guid: con otra cosa ni siquiera entran a la acción (404).


  

  
Todas las rutas, salvo las de /api/auth que son públicas (registro, OTP, login), exigen token. La columna «Roles» es el [Authorize(Roles = …)] del controlador.







  
Sección 8

  
Códigos HTTP

  
En breve
2xx salió bien, 4xx el cliente pidió algo que no corresponde, 5xx falló el servidor. La API usa un código preciso para cada caso, para que la web sepa qué mostrar sin leer el texto del mensaje.


  

    
CódigoCuándo lo devuelve la APICómo se produce en el código

    
      
200 OKConsulta o acción correcta con cuerpo.return Ok(dto) o return dto con ActionResult<T>.

      
201 CreatedSe creó algo: registro, proyecto, reserva, documento. Trae la cabecera Location con la URL nueva.CreatedAtAction(nameof(Obtener), new { id }, dto).

      
204 No ContentSe borró (proyecto en borrador, usuario sin actividad). Sin cuerpo.return NoContent().

      
400 Bad RequestDatos inválidos: falta un campo, fuera de rango, enum desconocido, monto bajo el mínimo.Automático por [ApiController], o ModelState.AddModelError + ValidationProblem().

      
401 UnauthorizedNo hay token, venció o no vale. En el login: correo o contraseña incorrectos.El middleware JwtBearer; en el login, Unauthorized(new LoginFallido(…)).

      
403 ForbiddenEl token vale pero el rol no alcanza. En el login: cuenta sin confirmar con OTP.[Authorize(Roles)]; en el login, StatusCode(403, …).

      
404 Not FoundNo existe o no es tuyo.NotFound(new Respuesta("No encontramos el proyecto.")).

      
409 ConflictLa petición está bien escrita pero choca con el estado actual: correo repetido, editar un proyecto que ya no es borrador, monto mayor que el cupo, pagar sin firmar.Conflict(new Respuesta(…)), casi siempre al atrapar TransicionInvalidaException o ReglaInversionException.

      
415 Unsupported Media TypeEl cuerpo no es JSON (falta Content-Type: application/json).Automático por [ApiController].

      
422 Unprocessable EntityVerificación de identidad con imágenes ilegibles: el formato está bien, el contenido no sirve.VerificacionController.Enviar.

      
423 LockedCuenta bloqueada 15 minutos tras 5 intentos fallidos (RF-02).StatusCode(423, new LoginFallido(…, BloqueadoHasta)).

      
500Error no previsto. Identity no pudo borrar un usuario.Problem(…) o una excepción no atrapada.

    
  


  
400 contra 409

  
Es la pregunta típica. 400: el pedido está mal armado y estaría mal en cualquier momento (plazo de 200 meses). 409: el pedido está bien, pero no se puede ahora por el estado del recurso (editar un proyecto que ya se envió a revisión). Mismo criterio para 401 contra 403: 401 es «no sé quién eres», 403 es «sé quién eres y no puedes».

Fluent API que conviene saber explicar

  

    
apps/api/Data/AppDbContext.csfragmentos


public class AppDbContext(DbContextOptions<AppDbContext> options)
    : IdentityDbContext<Usuario, IdentityRole<Guid>, Guid>(options)      // tablas de Identity con Id Guid
{
    // Todas las columnas decimal con 2 decimales (bolivianos, kg, litros)
    protected override void ConfigureConventions(ModelConfigurationBuilder c) =>
        c.Properties<decimal>().HavePrecision(18, 2);

    protected override void OnModelCreating(ModelBuilder b)
    {
        base.OnModelCreating(b);                                          // primero lo de Identity
        b.Entity<Usuario>(e =>
        {
            e.HasIndex(u => u.Ci).IsUnique();                             // CI único
            e.Property(u => u.EstadoVerificacion).HasConversion<string>(); // enum guardado como texto
        });
        b.Entity<ProyectoGanadero>(e =>
        {
            e.HasDiscriminator<string>("LineaProductiva")                   // TPH: una tabla, dos clases
                .HasValue<ProyectoEngorde>("Engorde").HasValue<ProyectoLecheria>("Lecheria");
            e.HasOne<Usuario>().WithMany().HasForeignKey(p => p.ProductorId);
        });
        b.Entity<HistorialProyecto>(e =>
            e.HasOne<ProyectoGanadero>().WithMany().HasForeignKey(h => h.ProyectoId)
             .OnDelete(DeleteBehavior.Restrict));                         // la bitácora no se borra en cascada
    }
}

  

  
    
    
  • Enums como texto (HasConversion<string>): en la tabla se lee EnRevision en vez de 1, y reordenar el enum no corrompe datos viejos.
    • 
    
  • TPH (table per hierarchy): ProyectoEngorde y ProyectoLecheria heredan de ProyectoGanadero y comparten la tabla Proyectos; la columna LineaProductiva dice cuál es. Las columnas de una sola línea quedan en NULL para la otra.
    • 
    
  • Relaciones sin propiedades de navegación: HasOne<Usuario>().WithMany() crea la clave foránea sin agregar proyecto.Productor. Por eso el código no usa Include: busca lo que necesita por id.
    • 
    
  • Restrict en vez de Cascade: borrar un proyecto o un usuario no puede llevarse puesta la bitácora ni las inversiones (RNF-03). Por eso, antes de borrar un borrador, el controlador borra a mano su historial, y un usuario con actividad no se puede eliminar (409).
    • 
    
  • Migraciones: se crean con dotnet ef migrations add Nombre -o Data/Migrations desde apps/api y la API las aplica con Database.MigrateAsync() al arrancar. La tabla __EFMigrationsHistory recuerda cuáles ya se aplicaron.
    •

Sección 10

  
DTO: class para entrar, record para salir

  
En breve
Los records también son DTO; no es «record en vez de DTO». DTO es el papel (un objeto que solo transporta datos por la API) y class o record es la forma de escribirlo. Convención del proyecto: lo que entra es una class con validaciones; lo que sale es un record, corto e inmutable.


  
Por qué existen los DTO

  
    
    
  • No exponer la entidad: Usuario tiene PasswordHash, SecurityStamp, contador de intentos… Devolverlo tal cual filtraría eso.
    • 
    
  • Evitar el over-posting: si el POST recibiera la entidad, alguien podría mandar "estado": "EnFinanciamiento" y publicarse solo. El DTO de entrada solo tiene los campos que el usuario puede tocar.
    • 
    
  • Contrato estable: se puede cambiar la base sin romper la web ni la app Android.
    • 
  


  
Qué es un record

  

    

      
Con class (como en clase)


public class RespuestaClase
{
    public string Mensaje { get; set; } = "";
}
// new RespuestaClase { Mensaje = "Listo" }

    

    

      
Con record (en el proyecto)


public record Respuesta(string Mensaje);
// new Respuesta("Listo")

    

  

  
Un record es una clase (tipo por referencia) para la que el compilador escribe lo repetitivo. Con la forma posicional, record Respuesta(string Mensaje), genera:

  

    
Qué generaQué significaEjemplo

    
      
Propiedades initSe asignan al crearlo y después no cambian (inmutable).r.Mensaje = "x" no compila.

      
ConstructorCon todos los parámetros, en orden.new Respuesta("Listo")

      
Igualdad por valorDos records son iguales si sus datos son iguales (dos class solo si son el mismo objeto).new Respuesta("a") == new Respuesta("a") → true

      
withCopia cambiando algún dato, sin tocar el original.var b = a with { Mensaje = "otro" };

      
ToString()Muestra los datos; útil en logs y pruebas.Respuesta { Mensaje = Listo }

      
DeconstrucciónSacar los valores en variables.var (mensaje) = r;

    
  


  
Por qué la salida es record y la entrada class

  
    
    
  • Salida → record: se crea una vez con todos sus datos y se serializa. Inmutable y en una línea; LoginResponse(Token, ExpiraEn, Usuario) se lee como la forma exacta del JSON. Igualdad por valor ayuda en las pruebas.
    • 
    
  • Entrada → class: los atributos de validación ([Required], [Range], [EmailAddress]) se escriben arriba de cada propiedad y los mensajes quedan legibles. Con records posicionales los atributos van en los parámetros (como el LoginSolicitud del Carrito) y es fácil confundir dónde aplican. También permite valores por defecto, como Aprobado = true.
    • 
    
  • Las dos funcionan con System.Text.Json: el serializador usa el constructor del record y los set de la class.
    • 
  


  

    
apps/api/Dtos/ProyectosDtos.cssalida, resumido


public record ProyectoDto(
    Guid Id, LineaProductiva Linea, string Nombre, string Ubicacion,
    decimal MontoRequeridoBs, decimal MontoMinimoBs, int PlazoMeses,
    EstadoProyecto Estado, DateTimeOffset CreadoEn, /* … */)
{
    // Método de fábrica: convierte la entidad en el DTO en un solo lugar
    public static ProyectoDto Desde(ProyectoGanadero p) => new(p.Id, p.Linea, p.Nombre, /* … */);
}

  

  
El mapeo entidad → DTO está en un método estático Desde dentro del record, en vez de un Select(new …) repetido en cada acción o una librería como AutoMapper. Si la entidad cambia, se corrige en un solo lugar.

  
Records ya aparecieron en la práctica del Carrito (ItemCarritoRespuesta, LoginSolicitud, TokenRespuesta), pero sin explicarlos. Lo que hay que saber decir: «un record es una clase con igualdad por valor e inmutable por defecto; la usamos para las respuestas porque son datos que no cambian después de crearse».







  
Sección 11

  
Validación y errores

  
En breve
Tres capas: los atributos del DTO (formato y rangos; 400 automático), las reglas del dominio que dependen de otros datos (en las clases del modelo y servicios; 400 o 409) y la base (índices únicos como último resguardo). Los errores de campos salen en el formato estándar ValidationProblemDetails; los demás, como { "mensaje": "…" }.


  

    
apps/api/Controllers/InversionesController.csReservar, resumido


if (usuario?.EstadoVerificacion != EstadoVerificacion.Verificado)
    return Conflict(new Respuesta("Tu identidad todavía no está verificada…"));        // 409: estado

if (req.MontoBs < proyecto.MontoMinimoBs)
{
    ModelState.AddModelError(nameof(req.MontoBs), $"El mínimo para invertir es {…}."); // 400 en el campo
    return ValidationProblem(ModelState);
}
if (req.MontoBs > cupo.LibreBs)
    return Conflict(new Respuesta($"El monto supera el cupo disponible: quedan {…}.")); // 409: cupo

  

  
    
    
  • [ApiController] hace tres cosas solo: responde 400 si el modelo no valida, lee el cuerpo como JSON sin poner [FromBody] y exige el Content-Type correcto (415).
    • 
    
  • ValidationProblemDetails es el formato del RFC 9110 / RFC 7807: type, title, status y errors con una lista por campo. La web lo usa para pintar el error debajo de cada casilla.
    • 
    
  • ModelState.AddModelError agrega a mano un error de campo que los atributos no pueden saber (el mínimo depende del proyecto), con el mismo formato que los automáticos.
    • 
    
  • Enums como texto: JsonStringEnumConverter(allowIntegerValues: false) hace que se envíe "Engorde"; un 7 da 400 en vez de guardar un valor inexistente.
    • 
    
  • Excepciones del dominio → 409: ProyectoGanadero e Inversion lanzan TransicionInvalidaException / ReglaInversionException si la acción no vale en su estado; el controlador las atrapa y responde 409 con el mensaje.
    • 
    
  • Mensajes que no revelan datos: «Correo o contraseña incorrectos» sin decir cuál falló; reenviar el OTP responde igual exista o no la cuenta.
    • 
  


  

    
  

  
Cualquier flecha que no esté en el dibujo es una transición inválida y la API responde 409. Las reglas viven en Models/Projects/States/EstadoFicha.cs (patrón State) y en Models/Investments/Inversion.cs.

    2. 
    
  2. appsettings.json: valores comunes, sin secretos.
    3.

    4. 
    
  4. User secrets: lo de cada máquina (dotnet user-secrets set …); viven fuera del repositorio.
    5.

    6.

    •

    • 
    
  • CancellationToken ct: casi todas las acciones lo reciben y lo pasan a EF Core. Si el cliente cierra la pestaña, la consulta a SQL Server se cancela en vez de seguir trabajando para nadie.
    • 
    
  • async/await en todo lo que toca la base o el correo: mientras SQL Server responde, el hilo atiende otras peticiones.

Sección 18

  
La web que la usa

  
En breve
La web en React + Vite llama siempre a /api/.... En desarrollo, Vite reenvía esas llamadas a https://localhost:7080 (proxy), así que el navegador cree que todo viene del mismo sitio y no hace falta CORS. El token se guarda en sessionStorage y se agrega en cada pedido.

  

    

      
apps/web/src/api.js


async function pedir(ruta, init = {}) {
  const headers = new Headers(init.headers)
  if (token) headers.set('Authorization', `Bearer ${token}`)
  return fetch(`/api${ruta}`, { ...init, headers })
}
// Un 401 fuera del login: token vencido → se borra y vuelve al login

    

    
  

  
    
    
  • sessionStorage y no localStorage: el token se borra al cerrar la pestaña. Menos tiempo expuesto si alguien usa la misma computadora.
    • 
    
  • Los errores 400 con errors se muestran debajo de cada casilla; un 403 se traduce a «Tu rol no tiene permiso para esta acción».
    • 
    
  • El menú muestra solo lo del rol, pero la seguridad real está en la API: aunque alguien escriba la URL a mano, sin el rol recibe 403.
