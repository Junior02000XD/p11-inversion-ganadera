Sección 1

El proyecto en un minuto

En breve

Esta es la primera sección: no necesitas nada previo.

El problema

En Santa Cruz hay productores de ganado (engorde de novillos y lecherías) que necesitan capital para comprar animales o alimento, pero no tienen garantías para un préstamo del banco. Del otro lado hay personas en la ciudad que querrían invertir montos chicos en ganado, pero no conocen a nadie del rubro y no confían en arreglos de palabra.

La solución

Una plataforma (web y Android) que conecta a los dos. El productor postula su proyecto, un analista técnico lo revisa y lo publica con sus riesgos, y los inversionistas aportan desde Bs 100. Todo queda registrado: quién firmó, cuánto pagó, qué pasó con el ganado y cómo se repartió el resultado.

Los cuatro roles

Se registra solo

Inversionista

Explora el catálogo, simula escenarios, invierte, firma el contrato con un código y paga con QR. Ve su portafolio y su constancia.

Se registra solo

Productor

Dueño del ganado. Sube los documentos de su predio, llena la ficha del proyecto y la envía a evaluación.

Cuenta interna

Analista

Equipo técnico. Revisa identidades y documentos, evalúa proyectos y los publica con riesgos y supuestos.

Cuenta interna

Administrador

Gestiona usuarios y roles, consulta la bitácora y puede operar todas las pantallas, con el selector «Ver como».

El recorrido de un proyecto

Un proyecto pasa por estos momentos. Los tres primeros están hechos (Sprints 1 y 2); los demás se construyen en el Sprint 3.

  1. Postular. El productor verifica su identidad, sube RUNSA y título del predio, y llena la ficha. Sprint 1 · RF-01 a RF-08
  2. Evaluar y publicar. El analista observa, rechaza o aprueba. Si aprueba, carga riesgos y supuestos y el proyecto entra al catálogo. Sprint 2 · RF-09, RF-10
  3. Invertir. Los inversionistas simulan, reservan cupo, firman con un código y pagan con QR. Reciben su participación y su constancia. Sprint 2 · RF-11 a RF-16
  4. Cerrar la ronda, comprar y trasladar el ganado. Sprint 3 · RF-17, RF-24, RF-25
  5. Registrar avances e incidencias (pesajes, mortalidad, reclamos al seguro), también sin conexión desde Android. Sprint 3 · RF-18 a RF-21
  6. Liquidar. Se vende el ganado, se descuentan costos y se reparte el resultado según la participación. Sprint 3 · RF-22, RF-23, RF-26

Regla de oro del proyecto (RNF-06): ninguna pantalla promete una ganancia segura. Toda rentabilidad se muestra como estimación, junto a sus riesgos.

Sección 2

Palabras clave

En breve

El sistema tiene dos partes que se hablan: la web (lo que ve el usuario en el navegador) y la API (el programa del servidor que aplica las reglas y guarda los datos en la base de datos). Aquí está el vocabulario para hablar de ambas.

Frontend (la web)

La parte que corre en el navegador: pantallas, botones, formularios. En P11 está en apps/web, hecha con React.

Es el mostrador de una tienda: lo que el cliente ve y toca.

Backend (la API)

El programa que corre en el servidor. Recibe pedidos, aplica las reglas del negocio y guarda en la base de datos. En P11 está en apps/api, hecho con ASP.NET Core.

Es la trastienda: donde se verifica, se cobra y se anota.

API

Conjunto de direcciones a las que la web (o Android) le pide cosas al servidor. Habla en JSON por HTTP.

Es la ventanilla con un menú fijo: pides algo de la lista y te responden.

Endpoint

Una dirección concreta de la API con su método, por ejemplo POST /api/inversiones (reservar cupo).

Una ventanilla específica: «depósitos», «retiros».

Métodos HTTP

GET consulta, POST crea o ejecuta una acción, PUT reemplaza (edita), DELETE borra.

Mirar, pedir, cambiar, cancelar.

Código de estado

Número con el que la API dice cómo le fue: 200 bien, 201 creado, 204 bien sin contenido, 400 datos inválidos, 401 sin sesión o credenciales malas, 403 tu rol no puede, 404 no existe (o no es tuyo), 409 choca con una regla o con el estado actual, 423 cuenta bloqueada.

Como el semáforo de un trámite: aprobado, observado, rechazado.

JSON

Formato de texto para mandar datos: { "proyectoId": "…", "montoBs": 1000 }.

Un formulario con casillas que las dos partes saben leer.

Base de datos relacional

Guarda los datos en tablas relacionadas entre sí (usuarios, proyectos, inversiones). En P11 es SQL Server.

Un archivador con carpetas que se citan unas a otras por número.

Tabla, fila, columna

Una tabla es un tipo de dato (Inversiones); cada fila es un registro (una inversión) y cada columna un campo (MontoBs).

Una hoja de Excel.

Clave foránea (FK)

Columna que apunta a una fila de otra tabla. Inversiones.ProyectoId apunta a Proyectos.Id.

En la boleta, el número de cliente que te lleva a su ficha.

ORM (Entity Framework Core)

Traduce clases de C# a tablas y consultas SQL. Escribes db.Inversiones.Add(x) y EF genera el INSERT.

Un traductor entre el idioma del programa y el de la base.

Migración

Archivo que describe un cambio en la estructura de la base (crear tabla, agregar columna). La API las aplica sola al arrancar. Hay dos: Inicial y Sprint2Inversiones.

El plano de una remodelación, con fecha, que se puede repetir en otra casa igual.

Entidad / Dominio

Las clases que representan el negocio y sus reglas: ProyectoGanadero, Inversion. Están en la carpeta Models/.

El reglamento interno de la empresa.

DTO

«Objeto de transferencia de datos»: la forma exacta de lo que entra o sale por la API (ReservaRequest, InversionDto). Separa lo que se muestra de lo que se guarda.

El formulario impreso que se entrega en ventanilla, distinto del expediente interno.

Controlador

Clase de la API que recibe los pedidos de un tema y responde (InversionesController). Debería ser delgado: valida, llama a las reglas y responde.

El cajero: atiende, pero sigue el reglamento.

Servicio

Clase con lógica que usan varios controladores (OtpService, GestorInversiones). Están en Services/.

Un área de apoyo: contabilidad, mensajería.

Inyección de dependencias

Las clases no crean lo que necesitan: lo reciben en el constructor. Program.cs dice qué clase se entrega para cada interfaz.

El restaurante no cría sus gallinas: el proveedor se las trae.

Interfaz

Un contrato: lista lo que una clase sabe hacer sin decir cómo (ICorreoService.EnviarAsync). Permite cambiar la implementación sin tocar a quien la usa.

El enchufe: cualquier aparato que lo respete funciona.

Autenticación vs. autorización

Autenticación: quién eres (login). Autorización: qué puedes hacer (tu rol). En la API, [Authorize(Roles = "…")] hace la segunda.

Mostrar el carnet en la puerta vs. tener pase a la zona VIP.

JWT (token)

Texto firmado que la API entrega al iniciar sesión. La web lo manda en cada pedido (Authorization: Bearer …). Dura 120 minutos y lleva el id, el correo y el rol.

La manilla de un evento: te la ponen al entrar y la muestras en cada puerta.

OTP

Código de un solo uso enviado por correo: 6 dígitos, vence en 10 minutos, 3 intentos. Se usa al confirmar la cuenta y al firmar el contrato de inversión.

El código que te manda el banco para confirmar una transferencia.

Hash

Huella de un dato que no se puede revertir. Las contraseñas y los OTP se guardan como hash, nunca en texto.

Como una huella digital: identifica, pero no reconstruye la mano.

Cifrado (AES-256-GCM)

Convierte un archivo en algo ilegible sin la clave. Las fotos del CI, la selfie y los documentos del predio se guardan cifrados (RNF-02).

Una caja fuerte: con la llave se abre, sin ella no.

Componente (React)

Una pieza de pantalla reutilizable, escrita como función: Tarjeta, Campo, Aviso. Cada pantalla de pages/ es un componente.

Piezas de Lego.

Estado (useState)

Lo que una pantalla recuerda mientras está abierta: lo que escribiste, el error a mostrar. Al cambiar, React vuelve a dibujar.

La pizarra del aula: se borra y se vuelve a escribir.

useEffect

Código que React ejecuta después de dibujar, por ejemplo pedir datos a la API al abrir la pantalla.

«Apenas abras la tienda, revisa el correo.»

Ruta

La dirección de una pantalla en la web: /catalogo, /inversiones/:id/contrato. Las define main.jsx.

El número de oficina dentro del edificio.

Proxy de Vite

En desarrollo, la web corre en el puerto 5173 y la API en el 7080. Vite reenvía todo lo que empieza con /api a la API, así el navegador cree que es un solo sitio.

La recepcionista que pasa la llamada al interno correcto.

Swagger / OpenAPI

Página que lista todos los endpoints de la API y permite probarlos («Try it out»). En /swagger.

El menú del restaurante, con la opción de pedir una probadita.

Prueba automática

Código que usa el sistema y verifica el resultado. Unitaria: prueba una clase sola. De integración: levanta la API entera y le hace pedidos reales. En P11 hay 112.

El control de calidad que revisa cada lote antes de salir.

Patrón de diseño

Solución conocida y con nombre a un problema que se repite al programar (State, Command, Prototype…). Ver la sección 9.

Una receta clásica: no la inventas, la adaptas.

Docker / contenedor

Forma de correr programas (SQL Server, Mailpit) ya configurados, sin instalarlos a mano.

Un contenedor de barco: llega cerrado y funciona igual en cualquier puerto.

Mailpit

Buzón falso para desarrollo: atrapa todos los correos de la API (OTP, avisos) y los muestra en http://localhost:8025. No envía nada de verdad.

Un buzón de práctica.

Git, rama, commit, pull request

Git guarda la historia del código. Un commit es una foto de un cambio; una rama es una línea de trabajo aparte; un pull request pide unir una rama a main con revisión.

Versiones de un documento con autor, fecha y comentario.

RF, RNF, CU

RF: requerimiento funcional (lo que el sistema hace, RF-01 a RF-27). RNF: no funcional (cómo lo hace: seguridad, usabilidad, RNF-01 a RNF-11). CU: caso de uso, una tarea completa de un actor.

RF: «la tienda vende». RNF: «y atiende en menos de 5 minutos».

Sprint, MV

Un sprint es un bloque de trabajo de dos semanas que termina con algo que funciona. MV1, MV2: versión mínima de cada sprint.

Entregas parciales de una obra.

Semilla (seed)

Datos que la API crea sola al arrancar: los roles y las cuentas internas (admin@p11.local, analista@p11.local).

El inventario inicial con que abre la tienda.

Servicio de fondo

Tarea que la API ejecuta sola cada cierto tiempo. VencimientoReservas revisa cada minuto las reservas vencidas, libera su cupo y avisa.

El guardia que da una vuelta cada hora.

No hay palabras que coincidan con esa búsqueda.

Web

React

Qué es: una biblioteca para armar pantallas con piezas reutilizables (componentes). Cuando cambian los datos, React vuelve a dibujar solo lo necesario.

Por qué: es la más usada, tiene muchísima documentación y el equipo ya la conocía. Las piezas comunes (Tarjeta, Campo, Aviso) se escriben una vez y se usan en las más de 40 pantallas.

En vez de: Angular (más pesado y con TypeScript obligatorio, más curva de aprendizaje) o Vue (parecido, pero con menos material en la carrera).

Web

Vite

Qué es: la herramienta que levanta la web en desarrollo (npm run dev) y arma la versión final (npm run build).

Por qué: arranca en un segundo y casi no necesita configuración. Su proxy reenvía /api a la API, así web y API parecen un solo sitio y no hay problemas de CORS.

En vez de: Create React App, que fue abandonado, o configurar webpack a mano.

Web

React Router

Qué es: permite tener varias pantallas con su dirección (/catalogo) sin recargar la página.

Por qué: cada caso de uso es una pestaña con su ruta, y las pantallas internas cuelgan de ella (/inversiones/:id/pago), así el menú marca dónde estás.

Web

JavaScript (sin TypeScript)

Por qué: menos curva para todo el equipo. Lo que se pierde: el editor no avisa si un dato tiene la forma equivocada. Para compensar, cada pantalla comenta arriba qué devuelve la API.

API

ASP.NET Core (.NET 10) y C#

Qué es: el framework web de Microsoft para escribir APIs en C#.

Por qué: es el que usa Programación Web 3; C# tiene tipos fuertes (muchos errores aparecen antes de ejecutar), trae Identity para usuarios, genera la documentación OpenAPI y tiene muy buen soporte para pruebas.

En vez de: Node con Express (más libre, pero sin estructura ni tipos por defecto) o Spring Boot (Java, más pesado de configurar).

Datos

Entity Framework Core

Qué es: el ORM: escribimos clases (Inversion) y EF crea las tablas, las migraciones y las consultas SQL.

Por qué: menos SQL repetido, migraciones versionadas en git y consultas con LINQ que el compilador revisa. Para las pruebas se cambia SQL Server por una base en memoria sin tocar el código.

En vez de: Dapper o SQL a mano: más control, pero mucho más código para lo mismo.

Datos

SQL Server 2022

Qué es: base de datos relacional de Microsoft.

Por qué relacional: los datos están muy relacionados (usuario → proyecto → inversión) y manejamos dinero, donde importa que todo sea consistente.

Por qué SQL Server: el proyecto empezó con PostgreSQL y se cambió el 18/11/2026 porque Programación Web 3 lo pide. Gracias a EF Core, el cambio fue de una línea (UseSqlServer) más una migración nueva.

Seguridad

Identity + JWT

Identity ya resuelve lo delicado: guardar contraseñas como hash, exigir correo confirmado, contar intentos fallidos y bloquear, y manejar roles. Hacerlo a mano sería riesgoso.

JWT: la API no guarda sesiones; cada pedido trae su token firmado. Sirve igual para la web y para Android.

En vez de: cookies de sesión, que funcionan peor con una app móvil.

Seguridad

OTP por correo

Por qué correo: la ERS v2.0 lo pide (RNF-01) y es gratis. En vez de: SMS, que cuesta por mensaje y necesita un proveedor.

Documentación

Swagger UI

Página que lista cada endpoint con sus parámetros, sus respuestas (200, 400, 404, 409, documentadas con [ProducesResponseType]) y un botón para probarlo con el token. La rúbrica de Programación Web 3 lo pide y sirve para mostrar la API sin la web.

Pruebas

xUnit + WebApplicationFactory

Levantan la API real en memoria y le hacen pedidos HTTP de verdad, con una base de datos en memoria y un buzón de correo falso. FakeTimeProvider deja adelantar el reloj para probar vencimientos (OTP a los 10 min, reserva a los 30 min) sin esperar.

Herramientas

Docker y Mailpit

Docker corre SQL Server y Mailpit sin instalarlos. Mailpit atrapa los correos para ver los OTP en la demo.

Sprint 3

Android en Java nativo

Por qué: el productor registra avances en el campo, muchas veces sin señal (RNF-04). Room guarda en el teléfono, WorkManager envía al recuperar la conexión y Retrofit llama a la misma API.

En vez de: Flutter o React Native: el trabajo sin conexión y el acceso al GPS y la cámara son más directos en nativo.

Sección 4

Cómo encaja todo

En breve

La web (React) corre en el navegador; la API (ASP.NET Core, en C#) corre en el servidor y es la única que habla con la base de datos (SQL Server). La web nunca toca la base: siempre le pide a la API. Después de iniciar sesión, la web guarda un token JWT y lo manda en cada pedido para decir quién es.

El dibujo general

Haz clic en un paso del recorrido de abajo y se marca en el dibujo la parte que trabaja en ese momento.

El viaje de un pedido: reservar Bs 1.000

Así viaja un clic desde la pantalla hasta la base de datos y de vuelta. Es el paso 1 del caso de uso «Invertir en un proyecto» (RF-13).

  1. La pantalla manda el pedido. En Invertir.jsx, el botón «Reservar cupo por 30 min» llama a api('/inversiones', { cuerpo: { proyectoId, montoBs: 1000 } }).apps/web/src/pages/investments/Invertir.jsx
  2. Se agrega el token. api.js pone Authorization: Bearer <token> y envía POST /api/inversiones. Vite lo reenvía a la API.apps/web/src/api.js · función pedir()
  3. La API revisa quién eres. Valida la firma del token. Si falta o venció: 401. Si tu rol no es Inversionista ni Administrador: 403. Lo hace el atributo [Authorize(Roles = …)].Controllers/InversionesController.cs · encabezado de la clase
  4. El controlador revisa la entrada y el contexto. ¿El monto es mayor a 0? ¿Tu identidad está verificada? ¿El proyecto está publicado y con la ronda abierta?InversionesController.Reservar()
  5. Se calcula el cupo libre. GestorInversiones suma lo pagado y las reservas vigentes de ese proyecto (las vencidas ya no cuentan).Services/Investments/GestorInversiones.cs · CupoAsync()
  6. Se aplican las reglas. Bajo el mínimo: 400 mostrando el cupo. Más que el cupo: 409. Otra reserva tuya en curso en el mismo proyecto: 409.InversionesController.Reservar()
  7. Se guarda. Inversion.Reservar(...) crea la reserva con vencimiento a los 30 minutos y db.SaveChangesAsync() hace el INSERT en la tabla Inversiones.Models/Investments/Inversion.cs · Data/AppDbContext.cs
  8. SQL Server guarda la fila con sus claves foráneas al proyecto y al usuario.tabla Inversiones
  9. Vuelve la respuesta. 201 Created con la inversión en JSON. La web lee su id y navega a /inversiones/{id}/contrato.Invertir.jsx · navegar(...)

Cómo funciona el inicio de sesión

  1. Login.jsx envía correo y contraseña a POST /api/auth/login.
  2. Identity compara la contraseña con el hash guardado. Si falla, suma un intento: al 5.º la cuenta se bloquea 15 minutos (423) y llega un correo de aviso. Si la cuenta no confirmó su correo: 403.
  3. Si está bien, TokenJwtService firma un token con el id, el correo y el rol, válido por 120 minutos.
  4. La web lo guarda en sessionStorage (sobrevive a recargar la página, no a cerrar la pestaña) y lo manda en cada pedido.
  5. sesion.jsx pide GET /api/auth/yo para saber quién eres, y el menú muestra solo las pestañas de tu rol (casosDeUso.js).

La web esconde las pestañas que tu rol no usa, pero la seguridad real está en la API: aunque alguien escriba la dirección a mano, la API responde 403 si el rol no corresponde.

2. Cómo la web llama a la API

apps/web/src/api.jsJavaScript
async function pedir(ruta, init = {}) {
  const headers = new Headers(init.headers)
  if (token) headers.set('Authorization', `Bearer ${token}`)
  try {
    return await fetch(`/api${ruta}`, { ...init, headers })
  } catch {
    throw new ErrorApi(0, 'No se pudo conectar con el servidor.')
  }
}

/** Llama a la API. Con `cuerpo` envía JSON; con `form`, archivos. */
export async function api(ruta, opciones = {}) {
  // … arma el método y el cuerpo
  const r = await pedir(ruta, init)
  if (!r.ok) throw await error(r, ruta)   // convierte 400/409 en un mensaje legible
  return r.status === 204 ? {} : await r.json()
}
  • Todas las pantallas usan api(...); nadie llama a fetch directo. Así el token y los errores se manejan en un solo lugar.
  • Si la API responde con error, error() arma un ErrorApi con el mensaje (mensaje) y los errores por campo (errors), que las pantallas muestran bajo cada casilla.
  • Un 401 fuera del login borra el token: la sesión venció.

3. Un controlador: reservar cupo

Controllers/InversionesController.csC#
[ApiController]
[Route("api/inversiones")]
[Authorize(Roles = $"{Roles.Inversionista},{Roles.Administrador}")]
public class InversionesController(AppDbContext db, GestorInversiones gestor, OtpService otp,
    UserManager<Usuario> usuarios) : ControllerBase
{
    [HttpPost]
    public async Task<ActionResult<InversionDto>> Reservar(ReservaRequest req, CancellationToken ct)
    {
        var usuario = await usuarios.FindByIdAsync(User.IdUsuario().ToString());
        if (usuario?.EstadoVerificacion != EstadoVerificacion.Verificado)
            return Conflict(new Respuesta("Tu identidad todavía no está verificada: …"));

        var proyecto = await db.Proyectos.FirstOrDefaultAsync(
            p => p.Id == req.ProyectoId && p.Estado == EstadoProyecto.EnFinanciamiento, ct);
        if (proyecto is null) return NotFound(new Respuesta("Ese proyecto no está en el catálogo."));

        var cupo = await gestor.CupoAsync(proyecto.Id, proyecto.MontoRequeridoBs, ct);
        if (req.MontoBs < proyecto.MontoMinimoBs) { /* … */ return ValidationProblem(ModelState); } // 400
        if (req.MontoBs > cupo.LibreBs)
            return Conflict(new Respuesta($"El monto supera el cupo disponible: quedan …"));    // 409

        var inversion = Inversion.Reservar(proyecto.Id, usuario.Id, req.MontoBs, gestor.Ahora);
        db.Inversiones.Add(inversion);
        await db.SaveChangesAsync(ct);
        return CreatedAtAction(nameof(Obtener), new { id = inversion.Id }, InversionDto.Desde(inversion, proyecto)); // 201
    }
}
  • [Route] fija la dirección; [HttpPost] dice que este método atiende POST /api/inversiones.
  • [Authorize(Roles = …)] deja pasar solo a inversionistas y administradores (si no, 403).
  • Lo que necesita (la base, el gestor, el servicio de OTP) llega por el constructor: es inyección de dependencias.
  • Cada regla que falla devuelve un código distinto: NotFound = 404, ValidationProblem = 400, Conflict = 409, CreatedAtAction = 201.
  • async/await: mientras espera a la base, el servidor atiende otros pedidos.

Sección 7

Casos de uso y pantallas

En breve

Un caso de uso (CU) es una tarea completa que hace un actor, como «Invertir en un proyecto». El docente pidió que cada pestaña del menú sea un caso de uso, con su nombre exacto del diagrama D1. Invertir en un proyecto (+ constancia en «Consultar portafolio»)

Sprint 2InversionistaRF-13, RF-14, RF-15, RF-16RNF-01, RNF-05, RNF-09

Es el corazón del Sprint 2. En cuatro pasos: reservar el cupo por 30 minutos, firmar el contrato con un código OTP, pagar con QR (simulado) y recibir la participación con su constancia.

Estados de una inversión

El cupo libre es: meta − lo ya pagado − las reservas que todavía no vencieron. Una reserva vencida o rechazada deja de ocupar cupo en el acto, y el inversionista recibe un correo.

Flujo paso a paso

  1. Reservar. Desde el simulador o la pestaña «Invertir» elige el monto. POST /api/inversiones → 201, estado Reservada, vence a los 30 min
  2. Leer el contrato. Ve el texto con su versión y los riesgos, y la cuenta regresiva. GET /api/inversiones/{id}/contrato
  3. Pedir el código. «Enviarme el código por correo». POST /api/inversiones/{id}/contrato/codigo
  4. Firmar. Marca «Leí y acepto» y escribe el código. Se guarda quién, cuándo y qué versión aceptó. POST /api/inversiones/{id}/contrato/firmar → Firmada
  5. Pagar. Se genera el QR con una referencia única; vence junto con la reserva. POST /api/inversiones/{id}/pago
  6. Confirmación de la pasarela (simulada con «Ya pagué, verificar»). Aprobado: Pagada, participación y constancia. «Simular pago rechazado»: Rechazada y cupo liberado. POST /api/inversiones/{id}/pago/confirmar
  7. Constancia y portafolio. Llega por correo y se ve en «Consultar portafolio». GET /api/portafolio · GET /api/portafolio/{id}/constancia

Cómo se calcula la participación (RF-16)

  • Porcentaje = aporte ÷ meta × 100. Ejemplo: 1.000 ÷ 100.000 × 100 = 1 %.

Sección 12

Preguntas para practicar

En breve

Piensa tu respuesta en voz alta y después ábrela para comparar. Si una respuesta usa una palabra que no conoces, búscala en Palabras clave.

General¿Qué problema resuelve el proyecto, en una frase?

Conecta a productores ganaderos que necesitan capital y no tienen garantías bancarias con inversionistas urbanos que quieren invertir montos chicos, con verificación, contratos y trazabilidad de cada boliviano.

General¿Qué entra en el Sprint 2 y cómo quedó?

Evaluación y publicación (RF-09, RF-10), catálogo con filtros (RF-11), simulador de tres escenarios (RF-12), y la inversión completa: cupo y reserva (RF-13), contrato con OTP (RF-14), pago QR simulado (RF-15) y participación con constancia (RF-16). Todo tiene endpoint, pantalla conectada y pruebas automáticas.

General¿Por qué el pago es «simulado»?

La ERS deja el proveedor de la pasarela «por definir». La API ya tiene los dos momentos reales de una pasarela: generar el cobro (QR con referencia y vencimiento) y recibir la confirmación. El botón «Ya pagué, verificar» hace de pasarela; cuando haya un proveedor real, solo cambia quién llama a /pago/confirmar.

General¿Qué significa que el Administrador «ve todo»?

Fue una corrección del docente: el Administrador está asociado a los 16 casos de uso, así que ve las 16 pestañas y la API lo deja pasar en todos los controladores. En los CU con varios actores elige «Ver como» Productor, Analista o Inversionista.

Tecnologías¿Por qué cambiaron de PostgreSQL a SQL Server?

Porque Programación Web 3 pide SQL Server. Como usamos Entity Framework Core, el cambio fue cambiar el proveedor (UseSqlServer) y regenerar la migración; el resto del código no se tocó.

Tecnologías¿Por qué React y no Angular?

Por la curva de aprendizaje y la documentación: React es más liviano, el equipo ya lo conocía y nos permite armar las pantallas con componentes comunes (Tarjeta, Campo, Aviso). Angular obliga a TypeScript y a una estructura más pesada.

Tecnologías¿Qué hace Vite además de levantar la web?

Arma la versión final optimizada (npm run build) y, en desarrollo, su proxy reenvía /api a la API. Así el navegador ve un solo sitio y no hay problemas de CORS.

Tecnologías¿Qué es Entity Framework y qué es una migración?

EF Core es el ORM: traduce clases de C# a tablas y consultas SQL. Una migración es un archivo con un cambio de la estructura de la base. Hay dos: Inicial y Sprint2Inversiones (tabla Inversiones y columnas de publicación). La API las aplica sola al arrancar.

Tecnologías¿Para qué sirve Mailpit?

Es un buzón falso para desarrollo: atrapa todos los correos de la API (OTP, avisos, constancias) y los muestra en localhost:8025 sin enviarlos de verdad.

Código¿Qué hay en Controllers, Dominio y Servicios?

Controllers: reciben el pedido HTTP, revisan roles y entrada, y responden con un código. Dominio: las clases del negocio con sus reglas (ProyectoGanadero, Inversion), sin saber nada de HTTP. Servicios: lógica que usan varios controladores (OTP, correo, cupo).

Código¿Qué es un DTO y por qué no devolver la entidad directamente?

Es la forma exacta de los datos que entran o salen por la API. Separarlo de la entidad evita exponer campos internos, permite validar la entrada con atributos ([Required], [Range]) y deja cambiar la base sin romper a la web.

Código¿Por qué Estado tiene private set?

Para que nadie de afuera pueda cambiar el estado a mano. Solo cambia por los métodos (FirmarContrato, ConfirmarPago…), que revisan las reglas antes. Si la regla no se cumple, lanzan una excepción y la API responde 409.

Código¿Qué es la inyección de dependencias? Da un ejemplo.

Las clases reciben lo que necesitan por el constructor en vez de crearlo. InversionesController recibe AppDbContext, GestorInversiones y OtpService; Program.cs decide qué se entrega. En las pruebas se cambia el correo real por uno en memoria sin tocar el controlador.

Código¿Cómo sabe la web qué pestañas mostrar?

De casosDeUso.js: una lista con los 16 CU, su ruta y sus roles. casosDe(rol) filtra la lista para el menú y RequiereSesion protege cada ruta. La seguridad real está en la API ([Authorize(Roles)]).

Código¿Dónde se valida el monto mínimo, en la web o en la API?

En la API (InversionesController.Reservar). La web solo muestra el mínimo y el cupo como ayuda y pinta el error que devuelve la API. Así la regla vive en un solo lugar y nadie la puede saltar desde Swagger o Android.

Casos de uso¿Qué pasa si el inversionista no paga en 30 minutos?

La reserva vence: deja de ocupar cupo en el acto, el servicio de fondo la marca como «Vencida» (revisa cada minuto) y le llega un correo diciendo que se liberó. Si intenta firmar o pagar después, la API responde 409.

Casos de uso¿Cómo se calcula el cupo libre?

Meta del proyecto − lo ya pagado − las reservas vigentes (reservadas o firmadas que no vencieron). Lo hace GestorInversiones.CuposAsync.

Casos de usoSi invierto Bs 1.000 en un proyecto de Bs 100.000 con 120 cabezas de 180 kg, ¿qué participación tengo?

1.000 ÷ 100.000 = 1 %. En kilos: 1 % × 120 × 180 = 216 kg de ganado. Queda en la constancia.

Casos de uso¿Qué necesita un productor para enviar su proyecto a evaluación?

Tres cosas, en este orden: la ficha completa y válida, su identidad verificada, y el RUNSA más el título de propiedad o el contrato de alquiler aprobados por un analista. Si falta una, la API responde 409 con el motivo.

Casos de uso¿Qué diferencia hay entre observar y rechazar?

Observar devuelve el proyecto a borrador con las observaciones para que el productor lo corrija y lo reenvíe. Rechazar es final: queda guardado con su motivo y no se publica. Los dos exigen texto y avisan al productor por correo.

Casos de uso¿Qué se exige para publicar un proyecto?

Que esté en revisión técnica y que el analista cargue el nivel de riesgo, el texto de riesgos y los cuatro supuestos de los escenarios (rendimiento, costos, mortalidad y variación) dentro de sus rangos. Si falta algo, 409 y no se publica (RF-10).

Casos de uso¿Cómo funciona el filtro «Monto mínimo hasta»?

Muestra los proyectos cuya inversión mínima es menor o igual al monto escrito. Responde a «¿en qué proyectos puedo entrar con Bs 500?».

Casos de uso¿Por qué el simulador muestra una advertencia?

Por RNF-06: ninguna pantalla puede mostrar rentabilidad como garantizada. Los escenarios son estimaciones con supuestos; el pesimista puede dar menos de lo invertido.

Seguridad¿Cómo se protege la contraseña?

Identity la guarda como hash (no se puede revertir), exige 8 caracteres con mayúscula, minúscula, número y símbolo, y bloquea la cuenta 15 minutos al 5.º intento fallido, con un correo de aviso.

Seguridad¿Dónde se usa el OTP y por qué?

Al confirmar la cuenta y al firmar el contrato de inversión (RNF-01). Prueba que quien actúa tiene acceso al correo. Se guarda solo su hash, vence a los 10 minutos y tiene 3 intentos.

Seguridad¿Qué evidencia queda de la firma del contrato?

En la inversión se guardan la versión del contrato, el correo de quien aceptó y la fecha y hora (RF-14). No hay ningún endpoint que borre inversiones, y las claves foráneas no borran en cascada.

Seguridad¿Cómo se protegen las fotos del CI?

Se piden solo con consentimiento explícito (RNF-07), se guardan cifradas con AES-256-GCM (RNF-02) y solo las abre su dueño o un analista, a través de un Proxy que registra cada acceso.

Seguridad¿Qué pasa si un inversionista pide la inversión de otro?

La API responde 404, como si no existiera: cada consulta filtra por el id del usuario del token. Así no se revela ni que existe.

Patrones¿Qué patrón usa el simulador y por qué?

Prototype: arma una configuración base con los supuestos del analista y la clona para el pesimista, el esperado y el optimista. Cada copia tiene sus propios supuestos y la base no se toca.

Patrones¿Cómo trabajan juntos State, Command y Observer al evaluar?

La decisión del analista se convierte en un Command. El gestor lo ejecuta: el State del proyecto decide si la transición vale (si no, 409), se guarda una fila en la bitácora y los Observers avisan al productor y a los analistas.

Patrones¿Por qué no usaron Mediator en el flujo de inversión?

Porque reservar, firmar, pagar y asignar son pasos en secuencia de una sola entidad, no objetos que conversan entre sí. Alcanza con la entidad Inversion y un servicio; Mediator sumaría una capa sin resolver nada.

Pruebas¿Cómo prueban que una reserva vence sin esperar 30 minutos?

Con FakeTimeProvider: un reloj falso que la prueba adelanta 31 minutos. Como la API pide la hora a ese reloj, cree que pasó el tiempo. Lo usa InversionesTests.

Pruebas¿Cuántas pruebas hay y cómo se corren?

112, todas en verde. Se corren con dotnet test desde apps/api. No necesitan SQL Server: usan una base en memoria.
