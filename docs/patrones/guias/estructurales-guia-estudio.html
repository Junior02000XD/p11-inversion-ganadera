1. Reparto de la exposición

Son siete patrones y cuatro personas. Se repartieron según lo que cuesta entender cada patrón y lo que hay que defender de él en el proyecto. Decorator y Proxy van juntos porque se escriben casi igual y la pregunta obvia del docente es en qué se diferencian, así que conviene que los explique la misma persona. Bridge va solo porque es el más difícil de explicar y el que más preguntas va a recibir («¿por qué no un Decorator?»). Flyweight es corto: termina en «no aplica» y se defiende con números.

2. Lo que los cuatro deben saber

Cualquiera puede recibir una pregunta sobre cualquier parte, así que esta base es común.

2.1 El documento en cinco ideas

  • Ahora hay código. La API del Sprint 1 (ASP.NET Core, .NET 10) está en el repositorio del equipo, p11-inversion-ganadera, y cada caso de estudio muestra código real y el comportamiento esperado del sistema.
  • Resultado: seis patrones aplican y están en el código (Adapter, Decorator, Proxy, Facade, Bridge y Composite, este último con encaje moderado). Flyweight no aplica.
  • No se inventaron problemas para usar patrones. Adapter ya existía (el envío de correo); Decorator y Facade salieron de reordenar código del Sprint 1; Proxy, Bridge y Composite responden a requerimientos concretos (RF-05, RF-02/04/20, RF-23).
  • Cuando un patrón encaja poco, se dice: Composite es moderado, Flyweight no aplica y el Proxy sería redundante si solo existiera la pantalla del analista.

2.3 Cómo se decidió si un patrón aplica

Se usaron tres preguntas, en este orden:

  • ¿Qué es lo que molesta en la estructura? Una interfaz ajena, varias piezas que hay que coordinar, responsabilidades mezcladas, un acceso que hay que controlar, dos cosas que cambian por separado, una jerarquía de parte y todo, o memoria repetida.
  • ¿Eso aparece en el código o en un requerimiento concreto?
  • ¿La alternativa simple (una interfaz con una implementación, un if, una lista) no alcanza?

Si las respuestas son «sí» a la segunda y «no alcanza» a la tercera, el patrón se justifica. Si no, se queda fuera y se explica por qué, como Flyweight.

2.4 Vocabulario que se repite

  • Delegar: un objeto le pasa el trabajo a otro que guarda como referencia. Todos los estructurales, salvo Flyweight, se apoyan en eso.
  • Cliente: la clase que usa el patrón sin saber qué hay detrás, por ejemplo un controlador u OtpService.
  • Adaptado: la clase ajena que se adapta (SmtpClient).
  • Sujeto real: el objeto que el proxy protege (VisorDocumentos).
  • Componente, hoja y compuesto: las tres piezas de Composite.
  • Abstracción e implementador: las dos jerarquías de Bridge (Aviso e ICanalAviso).
  • Estado intrínseco y extrínseco: en Flyweight, lo que se comparte y lo propio de cada objeto.
  • Inyección de dependencias: los objetos se crean y conectan en Program.cs, y cada clase recibe por el constructor lo que necesita.

3. Guía por integrante

Cada bloque trae lo que hay que entender, el código clave, dónde está en el proyecto, por qué se eligió ese lugar, las preguntas probables con una idea de respuesta y dos preguntas para comprobar que ya se sabe.

3.1 Integrante 1: Adapter y Facade (y apertura)

Apertura. Los patrones estructurales resuelven cómo se combinan clases y objetos sin que queden atados entre sí. Son siete, y hay que poder nombrarlos y decir en una frase qué problema resuelve cada uno (tabla de la sección 1). Casi todos usan la composición: un objeto guarda una referencia a otro y le delega trabajo. Lo que cambia de uno a otro es el motivo de esa delegación.

Adapter: qué hay que entender. El sistema espera una interfaz (ICorreoService, con un solo método) y la clase que hace el trabajo tiene otra (SmtpClient, que pide un MailMessage, direcciones y credenciales). El adaptador implementa la primera y por dentro usa la segunda. Solo traduce: no decide nada del negocio.

apps/api/Services/Email/CorreoSmtpService.cs

public class CorreoSmtpService(IOptions<CorreoOptions> opciones, ILogger<CorreoSmtpService> log) : ICorreoService
{
    public async Task EnviarAsync(string para, string asunto, string cuerpoTexto, CancellationToken ct = default)
    {
        using var cliente = new SmtpClient(_o.Host, _o.Puerto) { EnableSsl = _o.UsarSsl };
        // ...
        using var msj = ArmarMensaje(para, asunto, cuerpoTexto);
        await cliente.SendMailAsync(msj, ct);

Por qué ahí. Es la dependencia externa real que ya tenía el proyecto. Se evaluó crear un adaptador para el proveedor de identidad, pero como todavía no hay proveedor, habría que inventar su API, y eso habría sido artificial. Los próximos adaptadores serán la pasarela QR (RF-15) y el proveedor de identidad cuando se contrate (RF-03).

  • «Si ya estaba, ¿qué hicieron?» Lo identificamos, separamos ArmarMensaje para que la traducción quede en un solo método y lo documentamos. Además es el molde para la pasarela QR.
  • «¿No es solo una interfaz con una implementación?» La diferencia es que la implementación envuelve una API ajena con otra forma. Si la clase fuera nuestra, no habría nada que adaptar.
  • «¿Adapter de clase o de objeto?» De objeto: el adaptador usa un SmtpClient, no hereda de él. C# no permite heredar de dos clases, así que el de clase casi no se usa.

Facade: qué hay que entender. Un subsistema tiene varias piezas que hay que usar en cierto orden. La fachada ofrece pocas operaciones que las coordinan. No traduce una interfaz (eso es Adapter): simplifica varias.

apps/api/Services/Verification/VerificacionService.cs

public async Task EnviarAsync(Usuario usuario, IReadOnlyList<ImagenVerificacion> imagenes, CancellationToken ct = default)
// ...
public Task DecidirAsync(Usuario usuario, bool aprobar, string responsable, string motivo, CancellationToken ct = default) =>

Antes y después. VerificacionController coordinaba directamente el almacén cifrado, el proveedor, el umbral, el historial y el aviso, y AnalistaController repetía la secuencia «cambiar estado, guardar y notificar». Ahora los dos llaman a la fachada, y el método Enviar bajó de 54 a 32 líneas.

  • «¿Eso no es solo un servicio?» Sí, y una fachada casi siempre es eso: una clase de servicio que da una entrada simple a un subsistema. Lo que la hace fachada es que esconde cinco piezas detrás de dos operaciones y que los controladores dejaron de conocer esas piezas.
  • «¿Cambió algo para el usuario?» No. Sube su CI y su selfie, queda Verificado o En revisión, el analista decide con un motivo y siempre llega el aviso. Cambió la organización interna: ese flujo ahora está en un solo lugar.
  • «¿Dónde más se usaría?» En la inversión del Sprint 2: cupo, contrato, cobro QR y participación en una sola operación. En la web, api.js ya es una fachada sobre fetch, el token y los errores.

Buena práctica que le toca decir. El adaptador solo traduce, y la fachada coordina sin reemplazar al dominio: si crece, se arma una fachada por subsistema.

Para comprobar que ya se sabe. ¿En qué se diferencian Adapter y Facade? (Uno traduce una interfaz; la otra simplifica varias). ¿Qué habría que cambiar para pasar a MailKit? (Un adaptador nuevo y una línea en Program.cs).

3.2 Integrante 2: Decorator y Proxy (y comparación)

Decorator: qué hay que entender. El decorador implementa la misma interfaz que el objeto que envuelve y guarda una referencia a él. Hace algo antes o después y siempre delega. Como la interfaz es la misma, se pueden apilar.

apps/api/Services/Files/AlmacenCifrado.cs

public AlmacenCifrado(IAlmacenArchivos interno, IOptions<ArchivosOptions> opciones)
// ...
    aes.Encrypt(nonce, contenido, paquete.AsSpan(TamNonce + TamTag), paquete.AsSpan(TamNonce, TamTag));

return _interno.GuardarAsync(paquete, ct);

Dónde está. AlmacenDisco solo guarda bytes y AlmacenCifrado cifra y le delega (RNF-02). CorreoConReintentos envuelve al adaptador de correo y reintenta tres veces (RF-01). Los dos se componen en Program.cs. Un detalle a mencionar: el sistema se comporta igual que antes; los controladores que suben o abren documentos no se enteraron del cambio.

  • «¿Por qué no heredar, AlmacenCifrado : AlmacenDisco?» Con herencia, el cifrado queda pegado al disco. Con el decorador, si los archivos pasan a la nube se cambia el almacén interno y el cifrado sigue igual. Además, las capas se combinan sin crear una subclase por combinación.
  • «¿El orden importa?» Sí. Por eso la composición está en un solo lugar, Program.cs.
  • «¿Qué pasa si el correo falla las tres veces?» Se rinde y el error llega al registro, que ya le dice al usuario que pida que se le reenvíe el código.

Proxy: qué hay que entender. El proxy tiene la misma interfaz que el objeto real y se pone delante de él, pero decide si delega. El de protección controla permisos.

apps/api/Services/Documents/VisorDocumentosProxy.cs

if (!solicitante.IsInRole(Roles.Analista) && solicitante.IdUsuario() != dueno)
{
    // Se responde igual que si no existiera, para no confirmar que el documento está ahí.
    log.LogWarning("{Correo} intentó abrir el documento {Documento}, que no es suyo", solicitante.Correo(), documentoId);
    return null;
}

Por qué no alcanza con [Authorize]. Ese atributo solo mira el rol, y dos productores tienen el mismo rol. La regla es «el dueño del documento o un analista». Hoy usan el proxy dos controladores: el del analista y el endpoint nuevo del productor.

  • «¿Por qué 404 y no 403?» Para no confirmar que el documento existe. Es habitual cuando los identificadores se pueden probar uno por uno.
  • «¿No era mejor la autorización basada en recursos de ASP.NET?» Es la forma propia del framework y también sirve. La diferencia es que cada controlador tiene que acordarse de llamarla; el proxy protege aunque el que lo use no lo sepa. En el documento figura como alternativa.
  • «¿Dónde más?» En RF-22, el inversionista abrirá solo los documentos de los proyectos donde invirtió. En Android, Retrofit genera proxies remotos de la API.

La comparación que le toca. Se escriben casi igual: misma interfaz y una referencia al otro objeto. Decorator siempre delega y agrega algo; Proxy decide si delega. Un ejemplo para decirlo: se descartó un decorador de auditoría sobre el almacén porque registrar quién abre un documento depende del usuario, y eso ya lo hace el proxy.

Buena práctica que le toca decir. Un decorador, una responsabilidad, y el orden de la composición en un solo lugar. La regla de acceso va en el proxy y no repetida en cada controlador.

Para comprobar que ya se sabe. ¿Por qué AlmacenCifrado es un Decorator y no un Proxy? (Porque siempre delega). ¿Qué recibe otro productor que pide un documento ajeno? (Un 404, como si no existiera).

3.3 Integrante 3: Bridge (y Bridge frente a Decorator)

Qué hay que entender. En los avisos hay dos cosas que cambian por separado: qué se avisa (verificación, bloqueo y, más adelante, incidencias) y por dónde llega (correo, Telegram, push en Android). Sin el patrón haría falta una clase por combinación. Con el puente, el aviso guarda una referencia al canal y cada lado crece por su cuenta.

apps/api/Services/Notifications/Aviso.cs

public abstract class Aviso(ICanalAviso canal)
{
    protected abstract string Asunto { get; }
    protected abstract string Cuerpo { get; }
    protected virtual bool Urgente => false;

    public Task EnviarAsync(string destino, CancellationToken ct = default) =>
        canal.EntregarAsync(destino, new MensajeAviso(Asunto, Cuerpo, Urgente), ct);
}

Las piezas. Aviso es la abstracción; AvisoVerificacion y AvisoBloqueo son abstracciones refinadas. ICanalAviso es el implementador; CanalCorreo (en uso) y CanalTelegram (implementado) son implementaciones concretas. La push de Android (Sprint 3) sería un canal más.

La cuenta para decir. Con 3 avisos y 3 canales, sin puente serían 9 clases (AvisoBloqueoCorreo, AvisoBloqueoTelegram…). Con puente son 6. Cada aviso o canal nuevo suma una clase, no una por combinación.

Por qué no Decorator. Hay tres razones:

  • Decorator agrega capas a un mismo objeto, y Telegram no le agrega nada al correo: es una alternativa del mismo nivel.
  • Decorator maneja una sola dimensión, y aquí hay dos: el tipo de aviso y el canal.
  • El canal se elegirá según la preferencia de cada usuario, no con una cadena fija armada al iniciar.

Decorator sí sirve sobre un canal, por ejemplo para agregar reintentos, y eso ya se hace con CorreoConReintentos.

  • «¿CanalTelegram se usa?» Está implementado, pero no registrado en Program.cs, porque los usuarios todavía no tienen un chat vinculado. Activarlo es guardar ese dato y elegir el canal; ningún aviso cambia, que es justo lo que demuestra el patrón.
  • «¿Y el código OTP por Telegram?» No. El OTP comprueba que el correo es del usuario, así que tiene que llegar al correo.
  • «¿Bridge y Adapter no son lo mismo?» Se parecen en la forma. Adapter se aplica después, sobre algo ajeno que no se puede cambiar; Bridge se diseña antes para que las dos partes crezcan por separado. De hecho, CanalCorreo usa por dentro el adaptador de correo.
  • «¿Para qué está Urgente?» Lo decide el aviso (un bloqueo es urgente) y cada canal lo interpreta a su manera: en Telegram, un aviso urgente suena y uno normal llega en silencio.
  • «¿Dónde más?» En las constancias y los contratos (RF-14, RF-16): tipo de documento por un lado y formato de salida (PDF, HTML) por otro.

Buena práctica que le toca decir. Antes de usar Bridge, buscar las dos dimensiones; si solo varía una, alcanza con una interfaz y varias implementaciones.

Para comprobar que ya se sabe. ¿Cuál es la abstracción y cuál el implementador? (Aviso e ICanalAviso). ¿Qué hay que tocar para agregar la push de Android? (Una clase nueva que implemente ICanalAviso; ningún aviso).

3.4 Integrante 4: Composite y Flyweight (y cierre)

Composite: qué hay que entender. Es un árbol donde una hoja y un grupo comparten la misma interfaz, y el grupo delega en sus hijos. El que usa el árbol no pregunta qué tiene enfrente.

apps/api/Models/Settlements/ConceptoLiquidacion.cs

public class GrupoConceptos(string nombre) : ConceptoLiquidacion(nombre)
{
    // ...
    public override decimal TotalBs => _conceptos.Sum(c => c.TotalBs);

Números a saber. Los costos suman 62 000 Bs, con el subgrupo Sanidad (6 500 Bs) adentro. El resultado es 130 000 − 62 000 − 3 000 − 2 500 = 62 500 Bs. A un aporte de 20 000 Bs sobre 100 000 Bs le tocan 12 500 Bs. Son los mismos montos de la pantalla de liquidación de la web.

Por qué el encaje es moderado. Si los costos fueran siempre de un solo nivel, bastaría agrupar una lista por categoría. Se justifica por los subrubros con subtotales del informe de cierre y porque TotalBs funciona igual en cualquier nivel.

  • «¿No es sobreingeniería?» Es el de encaje más flojo de los seis, y lo decimos. Son cuatro clases chicas, y si mañana se divide un rubro, el cálculo no cambia.
  • «¿El reparto es así en la realidad?» Es provisional: la regla de reparto y la comisión están por definir con el cliente.
  • «¿Dónde más?» En el portafolio (RF-24: portafolio, línea y participación). En la web, el árbol de componentes de React ya es un Composite.

Flyweight: qué hay que entender. Cuando hay muchísimos objetos que repiten los mismos datos, se comparte la parte repetida. Lo intrínseco (los datos de la raza) es inmutable y se comparte; lo extrínseco (caravana y peso) es propio de cada animal.

Números a saber. Unos 100 bytes por animal: 30 KB en un lote de 300, 100 KB con 1 000 cabezas y 1 MB en el caso extremo de Android sin conexión (1 000 cabezas × 10 pesajes). El celular le da a cada app entre 128 y 256 MB, y una sola foto de 12 MP abierta ocupa unos 48 MB.

  • «¿Por qué no lo implementaron?» Porque ahorra kilobytes. Implementarlo solo para cumplir habría sido sobreingeniería. El código está en el documento como ilustración.
  • «¿Y en Android sin conexión?» El caso extremo da 1 MB, menos del 1 % de la memoria de la app. En el celular lo que importa son las fotos.
  • «¿La base de datos no hace lo mismo?» Sí: la raza está una sola vez en su tabla. Es normalización, y en disco da el mismo ahorro.

Cierre. Repasar la tabla 5.8 con una frase por patrón. Con los creacionales del trabajo anterior, la API usa nueve patrones GoF (tres creacionales y seis estructurales), cada uno ligado a un requerimiento concreto. Lo que sigue: el adaptador de la pasarela QR y la fachada de inversión en el Sprint 2, y la push de Android y el endpoint de liquidación en el Sprint 3.

Buena práctica que le toca decir. Medir antes de aplicar Flyweight y dejar escrita cada decisión en el repositorio (docs/patrones/README.md).

4. Preguntas que pueden caer a cualquiera

PreguntaIdea de respuesta
¿Seis patrones no es demasiado?Cada uno responde a un problema que se puede señalar en el código o en un RF. Dos salieron de código que ya existía. El que no tenía un problema real, Flyweight, quedó fuera.
¿El código es de ustedes?Sí. Está en el repositorio del equipo, en la API del Sprint 1.
¿Afectan el rendimiento?Agregan una llamada por capa, que tarda nanosegundos, frente a los milisegundos del disco, la red o el correo.
¿Qué diferencia hay entre Adapter, Decorator y Proxy?Adapter cambia la interfaz; Decorator la conserva y agrega algo; Proxy la conserva y controla el acceso.
¿Cómo se conectan los objetos?En Program.cs, con la inyección de dependencias de .NET. Ahí se decide qué decorador envuelve a qué y qué recibe cada controlador.
¿Qué patrón recomiendan para lo que sigue?Adapter para la pasarela QR y Facade para la inversión, los dos en el Sprint 2.
¿Cómo se nota que un patrón funciona?Por el comportamiento del sistema: el mismo aviso sale por otro canal sin cambiar su texto, un documento ajeno no se abre, el código OTP llega aunque el correo falle un momento.

5. Puntos débiles del documento y cómo responderlos

  • «Adapter ya existía.» Es cierto y no se oculta. Se identificó, se probó y es el molde para la pasarela QR. Inventar un adaptador nuevo habría sido peor.
  • «Facade es un servicio con otro nombre.» Una fachada casi siempre es un servicio. Lo que importa es que eliminó código repetido y que los controladores dejaron de conocer cinco piezas.
  • «Telegram no se usa.» Está implementado y no registrado a propósito. Que se pueda activar sin tocar ningún aviso es lo que demuestra el Bridge.
  • «Composite es sobreingeniería.» El documento lo califica de moderado y dice cuándo no haría falta.
  • «El Proxy repite lo que hace [Authorize].» [Authorize] mira el rol; el proxy mira al dueño del documento. Si solo existiera la pantalla del analista, sí sería redundante, y el documento lo reconoce.
  • «Flyweight quedó sin código en el repositorio.» A propósito: el ahorro es de kilobytes. El fragmento del documento muestra cómo sería.
